Ads Harness Audit

This audit covers what the MCP harness did in testing, what Claude did, what still needs Claude, and what stands between this system and a paying client. Every number comes from the 131-check feature test, the repository code or the 17–19 Nov sessions. Wherever a figure is an estimate, it says so.

The six questions, answered

What share of the work does MCP do?

For doing, MCP does almost all of it. It made every one of the 131 Meta reads, writes and safety checks. For thinking, it does almost none. Claude decided every recommendation, every report finding and every fix. By pipeline stage, MCP owns 5 of 10 stages outright, shares 1 and owns none of the 4 judgement stages (see the workload table). A single overall percentage would be invented, so this page doesn't give one.

How much value does MCP add?

It adds a lot of reliability and very little insight. The harness makes Meta access safe, repeatable and auditable: approval gates, budget caps, forced PAUSED on creation, and credential redaction. It produces no conclusions of its own. The 19 Nov ad review is an example. Every number in it came through MCP, and every finding in it, such as "56% of spend went to men", was worked out by Claude.

What happens if Claude is removed?

The plumbing keeps working: the dashboard, approvals, scheduled KPI snapshots, number-only weekly reports, fatigue checks, backups and health checks. The brain stops. Nothing turns data into advice unless a DeepSeek or OpenRouter key is added, and that path is untested. The scheduler is currently SCHEDULER=off.

Does it really reduce Claude's workload?

Partly. It removes API plumbing, safety checks and record-keeping from Claude's job. It does not remove analysis, recommendations or report writing. The analysis tools also expect Claude to fetch the metrics and pass them in, so Claude still moves the data between tools.

What has to change?

Move the judgement into the harness:

  • fetch-and-analyse pipelines;
  • a rule-based findings engine;
  • ranked next steps;
  • a generated client report.

A cheap model writes the narrative, and Claude only answers questions and approves changes. The roadmap at the end gives the order.

What's stopping a paid launch?

Four gaps:

  1. Competitor and market research are stubs that return hard-coded sample data.
  2. No client-ready report exists without Claude.
  3. No next-step or strategy engine exists.
  4. The system is set up for one business and has only been proven on one small account.

3. Real examples

MCP heavy lifting

Reading the whole account

One call per object type returned campaigns, ad sets, ads, insights and breakdowns, with paging, retries and redaction handled. Claude only named the tool and the account.

MCP share of this outcome: almost all of it.

MCP heavy lifting

Stopping unsafe changes

A ₹600 budget, an ACTIVE status and a token pasted into the arguments were all refused by code before anything reached Meta. That guarantee doesn't depend on Claude behaving well.

MCP share: all of it.

MCP heavy lifting

Building Engagement 2.0 safely

Claude wrote the specs. MCP validated them, forced PAUSED, queued each one for the user's approval, created it and read it back.

MCP share: the execution and safety half.

Claude had to step in

The 19 Nov ad review

MCP supplied the raw insights. Claude worked out that 56% of spend went to men, that Audience Network brought 59% of page views and no orders, and that WhatsApp chats cost ₹5–11. Claude then wrote the whole report.

MCP share: the data only. The value came from Claude.

Claude had to step in

Page reads failing with #190

The harness sent the system-user token to Page endpoints, so the reads failed. Claude traced the cause, added a Page-token swap to transport.ts, wrote 3 tests and rebuilt.

MCP share: none. This was a harness defect.

Claude had to step in

"Optimise my campaigns"

skill_campaign_optimization returned PENDING and asked for explicit operations. Deciding what to change is left to whoever calls it.

MCP share: it would only carry out Claude's decisions.

8. Making MCP the main engine

  1. Pipelines instead of single tools. account_review(period) fetches everything, calculates and returns structured findings in one call, so Claude stops shuttling metrics between tools.
  2. A findings engine as code. Turn the checks Claude did by hand into rules with thresholds: gender skew from Advantage+, a placement with spend and no orders, cost per result above target, frequency and fatigue, learning-phase stalls. Each finding should carry its evidence numbers.
  3. An action ranker. Map each finding to proposed operations, ranked by expected impact × confidence ÷ risk, and save them as draft approvals.
  4. A report generator. Fill a fixed client template from the findings. A cheap model (DeepSeek) writes only the plain-English sentences. Then the scheduler can send it weekly without Claude.
  5. Real competitor data. Use the Meta Ad Library API and Apify, store snapshots, and compare formats and angles over time.
  6. Claude's role. It answers questions about the stored findings, explains them and drafts the approval brief. A person still approves every change.

Score and verdict

5.5/10

Not ready to sell as a self-running product. It is ready for one or two friendly pilot clients, with an operator running Claude and the pilot sold as "managed with AI tools". The safe-execution layer is good enough for clients now. The intelligence layer doesn't exist outside Claude yet.

The score balances strong plumbing and safety (about 9/10) against no reasoning layer, fake research and one-line reports (about 2/10).

Roadmap, in priority order

  1. Delete or flag the fake research skills so no client ever sees made-up numbers. (days)
  2. Fix the open Meta bugs: the WhatsApp enum, the placement map and automatic UNCERTAIN resolution. (days)
  3. Build the findings engine and account_review pipeline from the rules in the 19 Nov review. (1–2 weeks)
  4. Build the report generator with metrics that follow the business type, set a DeepSeek key, turn the scheduler on and run one week unattended. (1 week)
  5. Make competitor research real with Decode and the Ad Library, moving the token into a header. (1 week)
  6. Build the action ranker that feeds the approval queue. (1–2 weeks)
  7. Run a second, larger account plus Google Ads and GA4, then build per-client onboarding. (2+ weeks)
